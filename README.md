# aws-vpc-architecture — Production VPC on AWS

**Live (temporary):** http://vpc-demo-alb-861434400.eu-west-2.elb.amazonaws.com &nbsp;·&nbsp; **Author:** [devgershon](https://github.com/devgershon)

> This deployment will be torn down after testing to keep costs under control. The NAT Gateway alone runs at about $32 a month, and that adds up fast. Everything is in Terraform and takes about 10 minutes to redeploy from scratch whenever I need it.

A production-grade VPC running a FastAPI service on EC2, backed by RDS PostgreSQL, fronted by an Application Load Balancer. The whole point of this project was to stop simplifying the networking. The previous three projects in this series all took shortcuts — public subnets for everything, no database, no real network isolation. This one is done the way you would actually set it up for a production workload.

Three separate network tiers, each with its own subnets, route tables, and security groups. The ALB sits in public subnets and accepts traffic from the internet. EC2 sits in private subnets with no inbound internet access — the only way in is through the ALB. RDS sits in isolated DB subnets with no internet route at all, not even for outbound traffic. The EC2 instances connect to RDS over a direct private path, and nothing else can reach the database.

There are no SSH keys and no open SSH ports. Access to the EC2 instances goes through AWS Systems Manager Session Manager, which uses VPC endpoints so the session traffic never leaves AWS.

---

## Architecture

```
Internet
    |
    v (port 80)
ALB — public subnet (AZ-a, AZ-b)
    |
    v (port 8000, from ALB only)
EC2 — private subnet (AZ-a)
  - FastAPI + psycopg2
  - Outbound internet via NAT Gateway only
  - No inbound from internet
  - Shell access via SSM Session Manager
    |
    v (port 5432, from EC2 only)
RDS PostgreSQL — DB subnet (AZ-a, AZ-b)
  - No route to internet whatsoever
  - Encrypted at rest
  - Only reachable from the EC2 security group
```

## Network design

| Subnet | CIDR | What lives here | Internet access |
|---|---|---|---|
| public-a | 10.0.1.0/24 | ALB, NAT Gateway | Yes (via IGW) |
| public-b | 10.0.2.0/24 | ALB | Yes (via IGW) |
| private-a | 10.0.10.0/24 | EC2 app server | Outbound only (via NAT) |
| private-b | 10.0.11.0/24 | Reserved | Outbound only (via NAT) |
| db-a | 10.0.20.0/24 | RDS primary | None |
| db-b | 10.0.21.0/24 | RDS standby | None |

The database tier has no route table entry pointing to the internet. This is not just a security group rule — it is a network-level constraint. Even if the RDS security group were misconfigured, there is no path for traffic to travel to or from the internet.

## Deploy it yourself

You need an AWS account with the CLI configured, Terraform installed, and the AWS Session Manager Plugin on your local machine.

### 1. Clone

```bash
git clone https://github.com/devgershon/aws-vpc-architecture.git
cd aws-vpc-architecture
```

### 2. Set the database password

Create a file at `terraform/terraform.tfvars` with your chosen password:

```hcl
db_password = "your-secure-password-here"
```

This file is in `.gitignore` and must never be committed to Git. The password ends up in the EC2 user data as an environment variable, so keep it sensible but do not use anything you use elsewhere.

### 3. Deploy

```bash
cd terraform
terraform init
terraform apply
```

This takes 8 to 12 minutes, and most of that is waiting for RDS to provision. When it finishes, Terraform prints the ALB URL, EC2 instance ID, RDS endpoint, and the exact SSM command to connect to the instance. Wait another 4 to 5 minutes after apply before hitting the URL — the EC2 bootstrap script needs time to install Python and start the app.

### 4. Connect to EC2 via Session Manager

```bash
aws ssm start-session --target i-YOUR_INSTANCE_ID --region eu-west-2
```

You get a shell into the instance with no SSH keys and no open ports. The SSM agent communicates through VPC endpoints so the session traffic stays entirely within AWS.

### 5. Test it

```bash
# Check the service is up and the database is connected
curl http://your-alb.eu-west-2.elb.amazonaws.com/

# Create a note
curl -X POST "http://your-alb.eu-west-2.elb.amazonaws.com/notes" \
  -H "Content-Type: application/json" \
  -d '{"title": "First note", "content": "RDS is reachable from the private subnet."}'

# Read it back
curl http://your-alb.eu-west-2.elb.amazonaws.com/notes
```

### 6. Destroy when done

```bash
terraform destroy
```

Do not leave this running. The monthly cost is around $75-80 and the NAT Gateway is responsible for most of it.

### 7. Set up GitHub Actions for automated deploys

Add these four secrets under `Settings -> Secrets -> Actions`:

| Secret | Value |
|---|---|
| `AWS_ACCESS_KEY_ID` | Your IAM access key |
| `AWS_SECRET_ACCESS_KEY` | Your IAM secret key |
| `EC2_INSTANCE_ID` | From `terraform output ec2_instance_id` |
| `ALB_DNS_NAME` | From `terraform output alb_dns_name` |

The pipeline deploys code updates via SSM Run Command — it pulls the latest code and restarts the service on the instance. No SSH involved.

## Design decisions worth explaining

**Three subnet tiers with separate route tables.** Most tutorials put everything in public subnets to keep the setup simple. That is fine for learning but wrong for production. Separating the tiers into public, private, and database subnets — each with its own route table — means the isolation is enforced at the network level, not just by security groups. The database tier has no internet route. You cannot accidentally misconfigure your way into a publicly accessible database.

**NAT Gateway over a NAT instance.** A NAT instance is a self-managed EC2 server that acts as a NAT device. It works, but you are responsible for patching it, keeping it available, and scaling it when traffic increases. A NAT Gateway is a managed AWS service with none of those concerns. It costs more per hour, but for anything beyond a personal project the reduced operational overhead is worth it.

**Session Manager over a bastion host.** A bastion is a small EC2 instance in a public subnet that you SSH into first, then use as a stepping stone to reach private instances. It works, but it requires an open SSH port, key pair management, and another instance to maintain and patch. Session Manager requires no open ports at all. Access is controlled through IAM policies rather than key files on your laptop. It is also the approach AWS now recommends for new deployments, so it is worth knowing.

**VPC endpoints for Session Manager.** EC2 instances in private subnets cannot reach the internet directly. Session Manager would normally communicate through the internet, which means it would not work from a private subnet without going via NAT. Instead, three interface VPC endpoints — for `ssm`, `ssmmessages`, and `ec2messages` — create private connections from the VPC directly to the SSM service. The session traffic stays within the AWS network entirely.

**App code embedded in user data via Terraform.** The original approach was to clone the app from GitHub during EC2 bootstrap. That failed for a reason that is not immediately obvious — see "what I ran into" below. The fix was to use Terraform's `file()` function to read `main.py` at plan time and inject its contents directly into the bootstrap script via `templatefile()`. No external dependency, no credentials needed on the instance.

## What I actually ran into

**RDS rejected the backup retention period on a free tier account.**

The first `terraform apply` failed partway through with this:

```
FreeTierRestrictionError: The specified backup retention period exceeds
the maximum available to free tier customers.
```

The original configuration set `backup_retention_period = 7`. AWS free tier does not allow automated backups — the maximum allowed is 0. Changed the value to 0, reran apply, and RDS provisioned fine. Worth noting because the error message is specific and clear, but you would not know to look for it unless you had hit it before.

**EC2 could not clone the app from GitHub during bootstrap.**

After the first successful apply, the ALB returned 502. Connecting via Session Manager and checking the cloud-init logs showed this:

```
fatal: could not read Username for 'https://github.com': No such device or address
```

The bootstrap script tried to clone the GitHub repo at instance boot time. EC2 instances can reach GitHub over NAT — that part works — but GitHub requires authentication for private repos, and the instance had no credentials configured. The clone failed silently, the systemd service was never created, and the app never started.

The fix was to remove the git clone entirely and use Terraform's `file()` and `templatefile()` functions to read the app code on the local machine at plan time and write it directly into the user data script. No GitHub credentials needed on the instance, no external dependency during bootstrap.

**The Session Manager Plugin was not installed locally.**

Running `aws ssm start-session` threw this:

```
SessionManagerPlugin is not found.
```

The AWS CLI handles authentication and sends the start-session request to AWS, but the actual session tunnel runs through a separate local plugin that needs to be installed independently. On a Mac it is a `.pkg` file downloaded from an S3 bucket. It is not installed alongside the AWS CLI and the error message does not tell you where to get it. Once installed, Session Manager worked immediately.

## Cost

This is the most expensive project in the series. It is worth running for a week to get comfortable with the setup, but destroy it after that.

| Resource | Approximate cost |
|---|---|
| NAT Gateway | ~$0.045/hour (~$32/month) plus data transfer charges |
| RDS db.t3.micro | ~$0.02/hour (~$15/month) |
| EC2 t3.micro | ~$0.01/hour (~$8/month) |
| ALB | ~$0.008/hour (~$6/month) |
| VPC Endpoints x3 | ~$0.01/hour each (~$22/month combined) |

Running for a week costs around $20. Running for a full month costs around $75-80. Run `terraform destroy` when you are done.
